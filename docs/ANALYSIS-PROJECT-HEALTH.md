## 一、整体评价

TBox 是一款基于 **WinUI 3 + .NET 8** 的原生 Windows
桌面工具箱，核心价值是把常用程序集中管理，并通过贴边面板、胶囊入口和快捷操作降低启动成本。

从项目文档和已审查代码来看，TBox 已经具备比较完整的产品雏形。README
中介绍的能力包括：

-   将工具拖入工具箱，并自动获取图标、描述和关键词；
-   工具搜索、多分组管理；
-   最多管理 4 个独立工具箱；
-   左右或顶部贴边，支持胶囊收起与悬停展开；
-   全局快捷键、系统托盘、开机自启动和单实例；
-   高 DPI、主题适配；
-   JSON 本地配置存储、备份与迁移；
-   Lite / Full 两种发行包。

## 二、最值得优先考虑的产品优化

以下按预期用户收益和产品价值排序。

### 1. 胶囊快捷入口支持自定义

目前胶囊入口如果固定展示当前分组的前三个工具，用户未必能把最常用的程序放在最顺手的位置。

建议支持：

-   用户自行选择哪些工具显示在胶囊中；
-   拖拽调整显示顺序；
-   收藏工具优先显示；
-   可选"最近使用"排序；
-   支持固定常驻项，不因最近使用而被挤掉。

**建议原则：**
胶囊不是简单展示列表的缩略版，而应该是用户最常用的快捷启动区。

### 2. 增加跨工具箱的全局搜索

这是最值得投入的效率功能之一。用户不应该先判断工具在哪个盒子、哪个分组，再逐层查找。

建议能力：

-   一次搜索所有工具箱和分组；
-   支持名称、描述、关键词搜索；
-   支持拼音首字母和模糊匹配；
-   支持键盘上下选择、Enter 启动、Esc 关闭；
-   记录搜索历史；
-   允许通过全局快捷键呼出。

快捷键可以考虑
`Ctrl + Shift + T`，但应提供设置入口，避免与用户已有快捷键冲突。

### 3. 收藏与最近使用

建议在工具数据中增加收藏状态，并维护最近使用记录。

典型交互：

-   收藏工具可以在全局搜索和胶囊中优先显示；
-   最近使用列表提供快速回到刚刚启动的工具；
-   收藏与最近使用是两个独立维度，不要互相覆盖；
-   用户可以关闭最近使用记录。

### 4. 本地使用统计

可以在本地为每个工具记录：

-   `launchCount`：启动次数；
-   `lastLaunchedAt`：最后启动时间；
-   `createdAt`：添加时间。

基于这些数据提供：

-   最常用工具；
-   最近使用工具；
-   长期未使用工具提示；
-   可选的使用频率排序。

统计应保持本地化，不需要上传用户行为数据。建议允许用户关闭统计或清空记录。

### 5. 多工具箱窗口生命周期优化

多盒子是 TBox 的重要能力，但需要关注窗口数量增加后的资源开销和交互冲突。

建议：

-   评估启动时是否必须创建所有面板窗口；
-   对非活跃工具箱采用按需创建或懒加载；
-   同一屏幕边缘的多个胶囊需要避让，避免相互遮挡；
-   后续再考虑跨工具箱拖拽和工具移动。

**优先级建议：**
先解决同边胶囊避让，再评估跨盒子拖拽。后者涉及更多状态同步和交互边界。

### 6. 图标管理完善

建议补充：

-   用户自定义图标；
-   对 PNG、ICO 等常见格式提供稳定支持；
-   SVG 可先转换为适合当前 DPI 的位图用于显示；
-   图标缓存清理和刷新；
-   文件变化后刷新图标；
-   缓存键综合考虑文件路径或文件标识、修改时间和
    DPI，避免错误复用旧图标。

### 7. 备份、恢复与导入导出

配置数据是用户长期使用的核心资产，建议把备份恢复做得更可靠。

建议能力：

-   导出全部工具箱配置；
-   单独导出某个工具箱；
-   从备份恢复；
-   自动保留最近 7 天的配置备份；
-   导入时进行版本检查和数据校验；
-   导出配置元数据即可，不默认复制用户的 EXE 文件。

导入恢复前应先备份当前配置，并在失败时保留原始数据。

### 8. 性能与资源占用优化

已有文档记录的参考数据包括：4 个盒子时工作集约 177.6 MB、空闲 CPU 约
0.14%、轮询间隔 50 ms、启动约 0.7
秒。这些数据值得保留为后续优化的基线，但需要明确测试机器、系统版本、盒子数量和测量方法，避免不同环境的数据直接比较。

可以继续评估：

-   图标按需加载；
-   非活跃窗口减少刷新；
-   根据窗口状态调整轮询频率；
-   减少不必要的布局刷新；
-   在多显示器、不同 DPI 缩放比例下进行验证。

### 9. Windows 原生集成

值得考虑的方向：

-   资源管理器右键菜单"添加到 TBox"；
-   开机启动状态检测与修复；
-   托盘菜单和状态提示；
-   重要操作使用 Windows 通知；
-   多显示器位置记忆与恢复。

其中，**资源管理器右键"添加到 TBox"**
的用户收益比较直观：用户发现一个常用程序时，可以直接从文件或快捷方式菜单添加，而不是先打开
TBox 再拖拽。

### 10. 安装、升级与发行体验

当前已有 Lite / Full 构建和 CI 发布流程，可以逐步补齐：

-   安装版与绿色版的定位和共存规则；
-   安装、卸载时配置数据保留策略；
-   版本升级前自动备份；
-   配置文件版本兼容和迁移；
-   更新日志；
-   自动检查更新；
-   升级失败后的恢复策略。

建议先解决数据保留、配置迁移和版本兼容，再实现自动更新。不要为了自动更新而牺牲用户配置安全。

## 三、最有机会形成产品差异化的三个方向

### 方向 A：Command Palette（命令面板）

这是最值得长期考虑的方向。

用户通过全局快捷键呼出一个轻量搜索框，输入关键词后即可搜索并执行操作。

第一阶段可以支持：

-   搜索并启动工具；
-   打开工具所在目录；
-   以管理员身份运行；
-   搜索工具箱和分组；
-   最近使用和收藏结果优先。

后续再扩展命令，例如打开设置、切换工具箱、执行内置操作等。

**价值：** 让 TBox 从"桌面工具收纳箱"进一步成为"Windows
工具启动入口"。这比单纯增加更多管理页面更容易形成使用习惯。

### 方向 B：全局收藏中心

提供一个跨工具箱的收藏视图，用户不必关心工具原本放在哪个盒子或分组。

收藏中心可以与全局搜索、胶囊快捷入口共享同一套收藏数据，避免重复维护。

### 方向 C：插件扩展机制

可以考虑支持内置或第三方扩展，例如：

-   IP 信息查询；
-   端口检测；
-   ADB 常用操作；
-   串口调试；
-   常用开发环境快捷操作。

但插件机制会带来 API
兼容、安全边界、权限和生命周期管理等成本。建议等核心功能和数据模型稳定后再做，不建议当前阶段优先投入。

## 五、源码静态审查发现的具体问题

这一部分是本次审查中最值得优先处理的工程问题。

### 1. DataStore：保存失败后可能丢失重试机会

文件：[`DataStore.cs`](https://github.com/yeqing17/TBox/blob/main/src/TBox.WinUI/Services/DataStore.cs)

审查关注点：

-   `SaveNow()` 开始时先将 `_dirty` 设为 `false`；
-   如果后续保存失败，目前只记录 `LastSaveError`；
-   保存失败后没有看到将 `_dirty` 恢复为 `true`
    或明确安排自动重试的处理。

潜在影响：

如果一次写盘失败，程序可能认为当前数据已经不需要保存，后续没有新的修改触发保存时，用户最后一次配置变更就可能没有落盘。

建议：

-   保存成功后再清除 dirty 状态，或在失败路径恢复 `_dirty = true`；
-   失败后安排延迟重试，例如 2 秒后重试；
-   连续失败时给出可理解的用户提示；
-   提供手动保存或立即重试入口；
-   退出流程中执行最终保存，并妥善处理失败结果。

**优先级：高。** 这是配置数据可靠性问题，应先于新增功能处理。

### 2. Launcher：开机启动注册失败对用户不可见

文件：[`Launcher.cs`](https://github.com/yeqing17/TBox/blob/main/src/TBox.WinUI/Services/Launcher.cs)

审查关注点：

-   `StartupEntry` 捕获异常时使用了空 `catch`；
-   注册失败时用户无法明确知道开机启动没有生效。

建议：

-   返回明确的成功/失败结果；
-   保留异常信息供日志诊断；
-   在设置页面显示当前开机启动状态；
-   启动时检查配置与系统实际注册状态是否一致；
-   提供一键修复或重新注册操作。

**优先级：中。**

### 3. BoxManager：`async void Start()` 不利于启动流程管理

文件：[`BoxManager.cs`](https://github.com/yeqing17/TBox/blob/main/src/TBox.WinUI/BoxManager.cs)

审查关注点：

-   `public async void Start()` 无法被正常 `await`；
-   调用方无法自然等待启动完成，也不便统一捕获异步异常。

建议：

-   改为 `Task StartAsync()`；
-   调用方使用 `await`；
-   在启动入口统一处理异常和启动失败状态；
-   让窗口初始化、工具箱恢复等步骤具有明确的完成边界。

**优先级：中。**

### 4. ShellHost：Win32 API 返回值需要统一检查

文件：[`ShellHost.cs`](https://github.com/yeqing17/TBox/blob/main/src/TBox.WinUI/Interop/ShellHost.cs)

重点关注的 API 包括：

-   `RegisterClassEx`
-   `CreateWindowEx`
-   `RegisterHotKey`
-   `LoadImage`
-   `Shell_NotifyIcon`

建议：

-   统一检查 API 返回值；
-   失败时记录 `Marshal.GetLastWin32Error()`；
-   将底层错误转换为可诊断的日志；
-   对托盘图标增加 Explorer 重启后的恢复处理，例如监听 `TaskbarCreated`
    消息并重新注册托盘图标。

**优先级：中。**

### 5. CI：目前冒烟测试不足以覆盖核心功能回归

文件：[`build.yml`](https://github.com/yeqing17/TBox/blob/main/.github/workflows/build.yml)

现有流程已经包含 Lite / Full 双包构建、发行文件检查、Windows App Runtime
安装、启动冒烟测试和 Release 上传等步骤，这是不错的基础。

但启动到 Activated 只能说明程序能进入启动阶段，不能证明核心功能都正常。

建议逐步增加以下测试：

  测试模块    建议覆盖内容
  ----------- ---------------------------------------------
  DataStore   JSON 读写、损坏恢复、版本迁移、保存失败重试
  Launcher    EXE、快捷方式、管理员运行、异常路径
  Search      名称、描述、关键词、拼音和模糊匹配
  多盒子      状态恢复、窗口创建与关闭、边缘避让
  Docking     贴边、收起、展开、多显示器
  DPI         100%、125%、150%、200%
  发行包      Lite / Full 安装、启动、升级和卸载

**优先级：中高。**
测试应围绕核心用户路径逐步建立，不必一次性追求庞大的测试体系。

## 六、建议建立的验收标准

新增功能不应只以"能运行"为验收条件。建议每个版本至少检查以下维度：

### 产品体验

-   常用操作能否通过键盘完成；
-   搜索结果是否覆盖所有工具箱；
-   胶囊内容是否可控、顺序是否可预测；
-   多盒子同时使用时是否遮挡或抢焦点；
-   高 DPI 和多显示器下是否保持正确位置。

### 数据安全

-   保存失败后是否能重试；
-   程序异常退出后配置是否可恢复；
-   导入错误配置是否会破坏现有数据；
-   升级前是否保留备份；
-   新旧版本配置是否兼容。

### 稳定性

-   Win32 API 失败是否有日志；
-   开机启动注册失败是否可见；
-   托盘图标是否能在 Explorer 重启后恢复；
-   Lite / Full 包是否都能完成核心流程。

### 性能

-   记录启动耗时、空闲 CPU、工作集；
-   固定测试环境和测试步骤；
-   至少测试 1 个、2 个、4 个工具箱；
-   对比优化前后的数据，而不是只看单次测量。

## 七、最终建议：当前最应该做什么

如果只选择五件事，我建议按这个顺序：

1.  **修复 DataStore 保存失败后的重试机制。** 先保护用户数据。
2.  **把 `BoxManager.Start()` 改为可等待的异步启动流程。**
    降低启动阶段的异常管理成本。
3.  **完善 ShellHost 的 Win32 错误处理和托盘恢复。**
    提高长期运行稳定性。
4.  **建立收藏、最近使用和胶囊自定义能力。**
    让用户更快启动真正常用的工具。
5.  **实现跨工具箱全局搜索 / Command Palette。** 这是最可能提升 TBox
    产品辨识度和使用频率的功能。

我的核心判断是：**TBox
当前不缺功能方向，真正值得投入的是把"可靠性"和"启动效率"做扎实。**
先确保配置不丢、窗口行为稳定，再通过收藏、胶囊自定义和全局搜索形成高频使用闭环。插件生态和复杂扩展可以放到更后面。
